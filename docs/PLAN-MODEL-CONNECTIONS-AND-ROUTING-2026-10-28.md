# План: подключения моделей, надёжность API и маршрутизация Jev

Дата: 28 октября 2026 года. Статус: оставшиеся работы, не отчёт о выполнении.
Исходное состояние: коммит `1f3be1c` и последующая локальная очистка устаревших
DeepSeek-профилей в личных настройках. Этот документ уточняет оставшуюся часть
[исходного проекта API-подключений](DESIGN-API-CONNECTIONS-2026-10-26.md).

## Результат, к которому идём

Пользователь подключает сервис, видит доступные модели, выбирает состав ролей и
запускает задачу. Выбор сохраняется автоматически и локально. Warden проверяет
доступность перед работой, сохраняет фактические результаты и понятно объясняет
остановку. Jev помогает выбрать усилие, а позднее — модель из разрешённого списка.

Названия программ, способы запуска и разработчики моделей не должны подменять
понятие подключения к сервису. DeepSeek через GonkaRouter остаётся моделью внутри
GonkaRouter; запуск через Orca остаётся способом исполнения роли. Наличие CLI
не означает подписку, бесплатный доступ или определённый способ оплаты.

## 1. Разделить сервис, подключение, модель и исполнение

**Почему.** Сегодня CLI-сервис частично определяется по `modelVendor()` профиля.
Из-за этого API-модель, запущенная через сторонний CLI, может снова попасть в список
как самостоятельный CLI-вендор. Исправления подписей и удаление двух старых файлов
не устраняют причину для других конфигураций.

**Что сделать.**

- Определить отдельные сущности: сервис, подключение/аккаунт, модель, исполнитель
  роли и её состав. Разработчик модели нужен для независимости ревью, а не для
  определения способа входа или тарифа.
- У CLI хранить явную привязку к реальному сервису/аккаунту. У API использовать
  connection. Codex, OpenCode и Orca описывать как клиент/исполнитель, а не как
  основание для появления дополнительного вендора.
- Не пытаться молча угадать сервис для старого CLI-профиля по имени модели.
  Неоднозначные записи показывать как требующие сопоставления. Не извлекать
  OAuth-токены или ключи из чужой программы ради классификации интерфейса.
- Предусмотреть просмотр миграции до записи, резервную копию, явное сопоставление
  неоднозначных записей и повторный запуск миграции без повторных изменений.
- Сохранять ограничения инструментов, права записи, правила независимости и
  возможность чтения старых отчётов. Смена модели не наследует старый допуск.
- Проверить жизненный цикл интерфейса: добавление сервиса, выбор модели и роли,
  смена аккаунта, автосохранение, отключение и удаление подключения.

**Где начинать.** `VendorSettingsService`, `Profile`, `UserConfig`,
`ModelSettingsService`, `RoleRosterEditor`, `RunReadiness`, `ModelSettingsUi`.

**Готово, когда.**

- Несколько профилей OpenAI и способы direct/Orca не создают дубликаты сервиса.
- DeepSeek через API отображается внутри соответствующего API-подключения.
- Два разных аккаунта не теряют отдельную авторизацию при объединении отображения.
- Неоднозначный старый профиль не получает придуманного поставщика или подписку.
- Автосохранение нескольких быстрых изменений переживает перезагрузку страницы;
  конфликт записи виден и не затирает чужую настройку.
- Миграция проверена на копии конфигурации, включая откат и повторный запуск.

## 2. Устойчивость API и безопасное восстановление

**Почему.** Во время живых проверок GonkaRouter GLM вернул HTTP 502; DeepSeek мог
пройти проверку рабочего артефакта, но затем не подтвердить свежий ping. JoinGonka
прошёл подготовку и ping, однако финальное ревью оборвалось сетевой ошибкой.
По одному коду `network_error` нельзя утверждать конкретную причину сбоя.

**Что сделать.**

- Сохранить безопасные структурированные причины: установление соединения,
  ожидание заголовков, получение тела, общий deadline, HTTP-ошибка, обрезанный
  ответ, неверный JSON, несовпадение модели или nonce. Не сохранять сырой текст
  исключений и ответов, способный содержать секреты.
- Сопоставлять запрос, профиль, этап и попытку; сохранять разрешённые request ID,
  статус, длительности, известные usage и стоимость.
- Проверить реальные сочетания лимитов времени, выходных токенов и reasoning.
  Обрезанный pong не должен выглядеть как потеря авторизации.
- Определить ограниченную политику повторов для временных ошибок. Различать
  запрос, точно не отправленный, и запрос с неизвестным результатом. Повтор может
  расходовать квоту даже при отсутствии полученного ответа.
- Не перезапускать автоматически весь кодинг после ошибки ревью. После изменения
  файлов сохранять кандидата и продолжать только незавершённый этап, если его
  контракт и состояние по-прежнему совпадают.
- Переключение на другого поставщика разрешать только по явно заданной политике.
  Ошибка авторизации не должна открывать браузер или менять модель незаметно.

**Где начинать.** `ApiExecutor`, `ModelCheck`, coding relay, `RoleRunner`,
`TaskLoop`, журналы попыток и сценарии продолжения.

**Готово, когда.**

- Тесты воспроизводят 429/502, разрыв соединения, медленное тело, output limit,
  неверную модель и отмену; различимые причины видны без раскрытия секретов.
- Повторы ограничены, учитываются и не дублируют изменение файлов.
- После отказа ревью кандидат сохраняется, а допустимое продолжение не запускает
  исполнителя заново.
- Живые результаты документированы отдельно для каждого сервиса и модели.

## 3. Закрыть полный пользовательский сценарий

**Почему.** Успех отдельных ping и unit-тестов не доказывает полную рабочую петлю.
Прежний смешанный прогон не завершился успешно: четыре CLI-участника выполнили
роли, но последнее API-ревью закончилось ошибкой. Старый тест DeepSeek через CLI
не является целевой конфигурацией после очистки.

**Что сделать.**

- Подготовить небольшую задачу с изменением поведения и проверяемыми условиями
  в тестовом проекте hello-world. Сохранить исходное состояние и имеющиеся правки.
- Использовать актуальную схему: настоящие CLI-подключения и DeepSeek/GLM через
  разрешённые API-сервисы. Не возвращать старый Codex-профиль DeepSeek ради теста.
- Включить Jev, проверки доступности, машинные проверки и обязательное ревью.
- Выполнить две разновидности: CLI-исполнитель с API-ревью и API-исполнитель
  через допущенный OpenCode с независимым CLI-ревью.
- Проверить остановку и продолжение после намеренного отказа одного этапа.
- Сохранить отчёт с запрошенной/сообщённой моделью, выбранным/переданным effort,
  версиями политик, артефактами ролей и полным списком пропущенных этапов.
- Проверить страницу решения. Приёмка и слияние остаются отдельными решениями
  пользователя; тест не нажимает accept автоматически.

**Готово, когда.** Обе разновидности дошли до состояния готовности кандидата для
пользователя со всеми обязательными проверками. По каждому API-сервису есть
собственное доказательство; исключение сервиса из теста явно отмечено как
незакрытая проверка. Ключи отсутствуют в сохраняемых результатах.

## 4. Расширить управление effort по возможностям моделей

**Почему.** Сейчас автоматическое применение использует ограниченное сопоставление
GPT-6 и Grok 4.7. Одинаковое название уровня не гарантирует поддержку у другой
модели; переданный параметр не гарантирует независимого подтверждения провайдером.

**Что сделать.**

- Описывать допустимые уровни и способ передачи effort в реестре возможностей
  модели/адаптера с источником и датой подтверждения.
- Для API, CLI и OpenCode реализовывать передачу отдельно; не добавлять поле
  только в журнал, если исполнитель его игнорирует.
- Предлагать Jev только поддерживаемые уровни. Не превращать неподдерживаемое max
  в другое значение без объяснения.
- Сохранять приоритет явных настроек задачи/запуска и обычное усилие при отказе Jev.
- Отдельно решить применение к подготовительному планированию: сейчас оно сохраняет
  свои настройки, а классификация меняет этапы исполнения.
- Проверить вопросы и порог на наборе простых, сложных и неоднозначных задач;
  текущий порог не считать доказанно оптимальным.

**Готово, когда.** Для каждого нового адаптера есть проверка фактически отправленного
параметра, обработки неподдерживаемого уровня и fallback. В отчёте различаются
предложенный, переданный и подтверждённый effort; отсутствие подтверждения обозначено.

## 5. Выбор моделей и рекомендации по ролям через Jev

**Почему.** Это следующий функциональный шаг после подбора effort. Сейчас Jev
советует роли, но не меняет обязательный состав и не выбирает модели автоматически.
Добавление произвольных моделей из общего каталога сделало бы результат непредсказуемым.

**Что сделать.**

- Дать пользователю отдельное включение автоподбора моделей; не смешивать его с
  уже существующим флажком effort.
- Формировать кандидатов из разрешённых пользователем участников роли, с учётом
  доступности, возможностей инструментов, контекста и независимости ревью.
- Получать типизированный выбор/распределение Jev только среди этих кандидатов.
  Не давать классификатору добавлять новых поставщиков или обходить допуск.
- Сохранять причину выбора, альтернативы, версию каталога и политики. При отказе
  или неопределённом ответе использовать явный порядок пользователя.
- Оценивать цену лишь там, где данные известны. Неизвестная стоимость не означает
  ни бесплатность, ни запрет. Денежный лимит остаётся необязательным.
- Сначала выбирать один раз перед запуском; смену модели между попытками и
  динамическое расширение workflow рассматривать отдельными изменениями.
- Рекомендации по ролям сначала показывать в объяснении. Любое будущее добавление
  этапов должно иметь заранее разрешённые шаблоны и границы числа вызовов;
  обязательное ревью не снимается.

**Готово, когда.** Журнал позволяет восстановить выбор; явно закреплённая модель
имеет приоритет; недоступная, неподготовленная или зависимая модель не выбирается.
При отказе Jev запускается обычная разрешённая конфигурация либо объяснимый отказ,
если допустимых кандидатов вообще нет.

## 6. Каталоги, новые версии и документация

**Почему.** API-каталоги уже загружаются, но локальные CLI-кеши могут устареть.
Версии Jev сейчас ограничены в `DecisionProfile`; появление новой версии пока
не обслуживается одним обновлением каталога. Исходный документ проекта содержит
исторические ограничения, часть которых уже снята реализацией.

**Что сделать.**

- Где клиент поддерживает безопасное обновление списка без inference, добавить
  такой источник. В остальных случаях честно показывать дату кеша и инструкцию
  обновления, не обещая актуальность по одному нажатию кнопки панели.
- Отделить наличие модели в каталоге от доступа конкретного ключа. Исчезнувшую
  модель отмечать, сохраняя настройку для разбора и явной замены.
- Не заменять выбранную модель «самой новой» автоматически при обновлении списка.
- Предусмотреть обновление версии Jev с проверкой совместимости Decisions API и
  явным подтверждением новой сообщаемой версии; точную проверку identity сохранить.
- Обновить исходный план и инструкции: убрать противоречия между ранним offline
  OpenCode и нынешним проверенным исполнением; пометить старые eval-сценарии как
  исторические. Не выдавать их профили за рекомендуемые личные настройки.

**Готово, когда.** Проверены устаревший кеш, отказ каталога, исчезнувшая модель,
неизвестная новая модель и несовместимая версия Jev. Пользователь может продолжать
с ручной конфигурацией; обновление списка само не меняет состав или доступы.

## Что не блокирует основной выпуск

- Строгий денежный бюджет и сверка полного счёта: отдельная возможность; обычная
  работа опирается на ограничения времени, количества вызовов и токенов.
- Передача API-подключений в удалённые Orca-исполнители: отдельная задача,
  не причина показывать Orca среди вендоров.
- Дополнительные coding harness и общий командный gateway: только при подтверждённой
  потребности, после устойчивого основного сценария.
- Полный браузерный OpenRouter PKCE-сценарий: отдельная живая приёмка, если этот
  способ входа предлагается пользователю; локальная проверка обмена кода её не заменяет.

## Как фиксировать выполнение

Для каждого этапа сохранять небольшой отчёт: изменения, пройденные проверки,
оставшиеся ограничения и ссылки на квитанции. Автоматические тесты и живые
проверки отмечать раздельно. Историческое число прошедших тестов не переносить
на новые изменения как свежий результат. Частичный успех провайдеров не обозначать
успехом всей петли.

Текущее состояние на 2026-10-29: разделение сущностей и миграция реализованы;
устойчивость API дополнена явным упорядоченным резервом. Обе приёмочные петли
дошли до ручного решения. Оставшаяся проверка остановки/продолжения петли B
подтверждена локально на Windows с настоящим OpenCode/OpenRouter DeepSeek и CLI
Codex: внешний Ctrl+C, сохранение кандидата, повторное использование implement,
повторные машинные проверки и успешное ревью. Подробности и ограничения — в
[отчёте этапа 3](ACCEPTANCE-STAGE3-2026-10-28.md#live-local-loop-b-recovery--2026-10-29).
Этот прогон не подтверждает доставку сигналов Linux или текущую надёжность Gonka.

Этап 4 выполнен: реестр возможностей управляет допустимыми уровнями и передачей
через CLI/Orca, API и OpenCode; квитанции различают выбранный, отправленный и
