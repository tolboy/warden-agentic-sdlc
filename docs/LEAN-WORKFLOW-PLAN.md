# Краткий обзор: Прагматичный SDLC для Solo Developer (Warden + Orca)

> **Статус документа:** Обзорный документ для человека.  
> **Нормативный источник истины:** [ADAPTIVE-WORKFLOW-PLAN.md](ADAPTIVE-WORKFLOW-PLAN.md).  
> При любых расхождениях в контрактах, инвариантах, терминологии, лимитах и порядке реализации **безусловную силу имеет ADAPTIVE-WORKFLOW-PLAN.md**. Все изменения сначала вносятся в генеральный план, затем отражаются в этом обзоре.

## 1. Концепция: Суверенное ядро и мобильная витрина

Главная цель — дать соло-разработчику максимальный рычаг: рутину делают агенты в чистых Git worktree, а человек контролирует процесс с рабочего стола или с телефона без риска сломать репозиторий.

* **Warden (Суверенное ядро):** Детерминированный арбитр на Java (ноль зависимостей, компиляция одним `javac`). Управляет жизненным циклом задачи, запускает объективные проверки (сборка, тесты, линтеры, CDP-браузер), ведёт неизменяемый ledger и реестр замечаний (`findings registry`). Строго следует правилу: **Warden ничего не мёржит сам** — `approve` фиксирует решение, отдельный `land` оформляет публикацию (коммит/пуш/PR).
* **Orca (Витрина и пульт управления):** Локальный менеджер изолированных Git worktrees, сессий агентов и терминалов. Предоставляет Agent Dashboard со статусами сессий, отображение активных действий воркеров и мобильное приложение для удалённого контроля, просмотра синтаксического diff и передачи решений человека через Decision Gate.

## 2. Два режима работы

Генеральный план разделяет задачи на два штатных пресета:

1. **`lean` (проектируемый default для повседневных задач):**
   * **Назначение:** Обычные фичи, доработки, типовые багфиксы.
   * **Схема:** Интерактивный draft $\rightarrow$ Implementer $\rightarrow$ Machine Gates $\rightarrow$ Reviewer $\rightarrow$ (при P1: **не более одной** попытки repair) $\rightarrow$ Gates $\rightarrow$ Recheck $\rightarrow$ Human Gate.
   * **Ревьюер:** По умолчанию строгая независимость вендоров. Как явный проектируемый opt-in — режим `same_vendor_peer` (разные проверенные модели одного вендора для разработчиков с одной подпиской; в отчёте честно маркируется как соавторское peer-ревью, независимость не заявляется).
   * **Остановка Fail-Fast:** Если после одной попытки ремонта блокер не снят (`blocking_findings_remain`), либо подтверждённые блокеры повторяются без прогресса в уликах — немедленная передача человеку.
2. **`adaptive` (проектируемый opt-in для сложных расследований):**
   * **Назначение:** Задачи с высокой неопределённостью, исследование багов внешних интеграций.
   * **Схема:** Подготовка драфта с Opus-планером, эскалация моделей по ступеням (Grok $\rightarrow$ Opus $\rightarrow$ Astra) при исчерпании попыток качества, отслеживание множества авторов изменений (`writer_vendors`) и обязательный независимый финальный аудит кандидатов.

## 3. Как выглядит рабочий процесс на практике

1. **Подготовка задачи:**  
   Команда `warden do --draft-only` (с опциональным read-only планером при сложной цели) собирает черновик контракта `task.yaml`. Разработчик видит предложенный скоуп файлов, команды проверок и сценарии Visual QA, подтверждает или корректирует их за 30 секунд.
2. **Исполнение в чистом окружении:**  
   Warden запрашивает у Orca изолированный worktree. Воркеры запускаются с ограничением времени вызова (для коротких задач используются профили с `limits.wall_clock_minutes: 5` или `8`). В Orca отображаются сессии воркеров и опубликованные действия (запуск тестов, чтение файлов).
3. **Остановка на Human Gate и удалённое ожидание:**  
   При успешном прохождении проверок или при исчерпании ремонта Warden останавливается на человеческом гейте. В рамках Lean MVP добавляется ограниченный по времени слушатель (`--wait-for-gate [TTL]`), который держит процесс в режиме ожидания. В Orca карточка переходит в состояние, требующее внимания (`Needs You`), с push-уведомлением на телефон.
4. **Решение с телефона:**  
   Разработчик открывает приложение Orca Mobile, просматривает изменения во вкладке Diff и выбирает действие (`Accept` / `Reject`). Слушатель на ПК перехватывает ответ, выполняет полную валидацию (привязка к run/gate, версия решения, совпадение отпечатка кандидата, дедупликация) и сохраняет `decision.json`.
5. **Публикация:**  
   Принятый кандидат публикуется отдельной явной командой `warden land` (создание коммита, ветки или PR).

## 4. Границы доказанного и проверяемые цели

| Компонент | Статус на 2026-09-09 | Пояснение |
| :--- | :--- | :--- |
| **Резервирование бюджета (P0)** | ✅ Реализовано | Атомарный резерв числа вызовов до старта, сохранение вердиктов при resume. Денежный `max_cost_usd` — порог known spend, а не строгий cap (unpriced calls не ограничены суммой). |
| **Реестр замечаний (P1)** | ✅ Реализовано (suite 1383/0) | Устойчивые ID замечаний, типизация категорий, накопление закрытых findings. Ожидает формального принятия человеком. |
| **Десктопный lifecycle Orca** | ✅ Проверено (smoke 2026-09-04) | Запуск воркеров в Agent Dashboard (`WORKING 1`), settlement, освобождение терминалов, CLI-импорт решений. |
| **Mobile Diff, Push & Gate UI** | 🟡 Проверяемая цель | Документировано в Orca Mobile beta. Совместимость версий, отображение нативного Gate UI и надёжность push требуют проверки сквозным smoke-тестом. |
| **Слушатель `--wait-for-gate`** | 🟡 Проектируется (Lean MVP) | Bounded polling (5–10 сек), дедупликация, проверка отпечатка. Отдельный `gate_ttl` не сжигает бюджет времени исполнения агентов (`execution_deadline`). |
| **Квоты вендоров** | 🟡 Проектируется | Квоты в UI Orca — advisory (для глаз человека). В Warden: разделение кратковременного RPS 429 (backoff) и реального исчерпания баланса (failover confirm). |
| **Цель «10–15 минут»** | 🎯 Целевой ориентир (SLO) | Измеряемый ориентир для класса небольших задач, а не математическая гарантия. Быстрый таймаут не считается успешным завершением. |

## 5. Очерёдность реализации (согласно генеральному плану)

Переход между фазами является строгим гейтом:

1. **Подтверждение P1:** Формальное принятие кандидатов P0/P1 человеком по их собственным отпечаткам.
2. **Фаза P2:** Проверяемый draft до платного исполнения (`warden do --draft-only`, bootstrap contract, фиксация скоупа и проверок).
3. **Фаза P3 (Lean Core):** Пресет `lean` с `max_fix_attempts: 1`, накопительный счётчик repair через resume, опциональный `same_vendor_peer` с честной маркировкой.
4. **Фаза P4 (Бюджет и Quota MVP):** Разделение RPS rate limit (429) и исчерпания подписки, общий execution deadline цепочки, отдельный gate TTL, профили с короткими таймаутами.
5. **Фаза P5 (Orca Listener в составе Lean MVP):** Карточки задач, слушатель `--wait-for-gate`, сквозной интеграционный тест мобильного решения на зафиксированных версиях Orca.
6. **Фаза P3 (Расширенный Adaptive):** Множество `writer_vendors`, лестница эскалации моделей и независимый финальный аудит для сложных расследований.
