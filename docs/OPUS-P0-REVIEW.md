## 1. P1: новый контракт reviewer не проверяется при resume

Точки: `TaskLoop.reusableJudgements`, строки 1501–1613;
`WardenTree.snapshot/acceptanceDigest`.

Воспроизведение: implement и review прошли, browser остановился с
`visual_qa_unavailable`. В отдельном user config меняем reviewer roster с
`loop-review` на `audit-review` другого вендора; stage остаётся `review`.
Новый stub-reviewer настроен возражать. Продолжаем тот же кандидат.

Факт: `ready_for_human`, `role_runs=0`, старые `implement` и `review` переиспользованы.
Нового обязательного reviewer никто не вызывал.

Причина: оба hash покрывают проектную `.warden`, но не внешний user policy,
workflow, profile, prompt/schema. Имя stage само по себе не доказывает соответствие
новым требованиям к этой стадии. В исходном P0 требовался также policy/profile contract.

Нужно: сохранять и проверять семантическую идентичность judging stage и её
эффективного контракта, включая требования независимости, профиль и применимые
prompt/schema. Операционные изменения вроде разрешённого повышения лимита отделить
от изменений того, кто и по каким правилам должен судить работу. Не инвалидировать
все незатронутые стадии без необходимости. Для старых summary без доказательств
применять консервативный отказ от reuse соответствующего review.

Тесты: смена reviewer roster; изменение independence; изменение prompt/schema;
изменение workflow при том же stage ID; бюджетное повышение по-прежнему сохраняет
подходящий verdict, и `review` не заменяет `review-second`.

## 2. P2: корректный reuse теряет статус пройденного review

Точка: `TaskLoop.runRole`, строки 1207–1218, и `describeCompletion`.

Воспроизведение: существующий сценарий `reusedJudgementChecks`, run `ru2`.
Факт: `ready_for_human`, `role_runs=0`, `pending_stages=[]`, но
`candidate_review_passed=false` и `review_coverage` отсутствует.

Причина: ветка reuse переносит step и возвращает null, не восстанавливая coverage.
`warden report --text` на таком результате утверждает, что кандидат не прошёл review.

Нужно: восстанавливать проверенную coverage с origin run, stage, profile и
candidate identity. Различать `reused` и `executed_now`; reuse не должен начислять
новый вызов и не должен притворяться новым запуском в Dashboard.

Тест: продолжение с нулём платных вызовов сохраняет clean review, coverage и
правильные JSON/text статусы. Непроверенные или устаревшие verdict не становятся pass.

## 3. P2: проваленный recheck остаётся завершённой стадией

Точки: `TaskLoop.fixRound`, строки 798–821; `finished` и `describeCompletion`.

Воспроизведение: существующий `recheckFindingsChecks`, run `rk1`.
Review сначала проходит, после browser repair возвращает P1.

Факт: run правильно останавливается с `blocking_findings_remain`, но
`completed_stages=[implement,gates,review]`, а в `pending_stages` только `browser`.
Стадия review, которая только что провалилась, остаётся завершённой.

Нужно: при изменении кандидата инвалидировать затронутые completion/coverage,
а после успешного recheck устанавливать их заново. На всех аварийных выходах
не оставлять прежний pass применимым к изменённому кандидату.

Тесты: recheck с P1; execution failure; остановка между repair и recheck;
успешный recheck. Проверять не только общий `ok`, но и pending, coverage,
candidate identity и допустимость последующего reuse.

## 4. P2: при денежном стопе советуется менять лимит вызовов

Точка: `TaskLoop.safeNextStep`, строки 2053–2067.

Воспроизведение: `max_role_runs=20`, `max_cost_usd=0.01`, stub implementer
отчитывается о стоимости `0.012`.

Факт: `budget_stop="max_cost_usd of 0.01 reached, spent 0.012"`, но
`safe_next_step` рекомендует увеличить `budgets.max_role_runs`.
Это не устраняет причину остановки.

Нужно: структурированный тип бюджетного стопа и next step для соответствующего
ограничения. Проверить calls и money отдельно в summary и `report --text`.
Учёт цены после вызова не гарантирует строгий денежный резерв; это ограничение
должно оставаться явно обозначенным, как и отсутствие оценки неизвестных цен.

## Решение по отклонению бюджетной политики

Частичное продвижение с оплаченным review имеет ценность, поэтому запрещать его
во всех случаях не нужно. Но утверждения «repair всегда улучшает дерево» и
«отказ не сохраняет вызовы» не являются гарантиями. Repair может дать регрессию,
а человек может решить вообще не продолжать задачу.

Сделать режим явным в policy: полный резерв цепочки либо частичный результат
с достаточным резервом на необходимую повторную проверку. Для выполнения исходного
плана полный резерв — безопасный default; частичный режим включается настройкой,
отражается в dry-run, summary и Dashboard. Обновить противоречащие текущему
поведению комментарии `CallPlan.reserveForRepair` и `TaskLoop.requireReserve`.

Отдельно проверить repair на machine-gates до первого review: сейчас
`repairCost` может равняться одному вызову. Если частичный режим обещает именно
review результата, а не только повтор machine-gates, такой резерв недостаточен.
