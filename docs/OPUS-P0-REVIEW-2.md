Платный live и provider inference не проверялись. Удалённая конфигурация прежнего

## P1-A. Reuse не доказывает, что verdict относится к текущему кандидату

### Сценарий A1: implementer заново пишет во время resume

1. Первый run проходит implement и review, останавливается на отсутствии браузера.
2. Меняем только внешний контракт implementer. Reviewer остаётся прежним.
3. Resume правильно отклоняет reuse implement-стадии и вызывает implementer заново.
4. Stub implementer добавляет `src/partial.txt`: итоговый source fingerprint
   отличается от fingerprint первого run.

**Факт:** `role_runs=1`, переиспользован `review`, `ready_for_human`,
`candidate_review_passed=true`, `workflow_incomplete=false`.
Новое дерево никто не пересмотрел. Coverage хранит fingerprint прежнего дерева.

Точки: `TaskLoop.runRole`, строки 1247–1279. Пул reuse проверяется только в начале
run; условие `attempt == 0` не исключает повторный обычный implement dispatch.
`candidateAboutToChange()` вызывается только в `fixRound`.

### Сценарий A2: resume воскрешает уже инвалидированный review

1. Review проходит. В workflow для него `recheck_after_fix: false`.
2. Browser вызывает repair; stub implementer добавляет `src/after-repair.txt`.
3. Browser после repair становится недоступным; run останавливается с
   `visual_qa_unavailable`.
4. Первый run правильно пишет `review_coverage=[]`,
   `stages_judging_an_earlier_candidate=[review]`, `candidate_review_passed=false`.
5. Продолжаем это же дерево без новых изменений конфигурации.

**Факт:** resume получает `role_runs=0`, переносит старый review и пишет
`candidate_review_passed=true`, `ready_for_human`.
Более того, `carryCoverage` присваивает старому verdict fingerprint нового дерева.

Точки: `TaskLoop.reusableJudgements`, строки 1720–1773;
`carryCoverage`, строки 1325–1342. Reuse читает успешные строки `steps`, но
не учитывает их инвалидированность и fingerprint того кандидата, который реально
проверялся. Совпадение текущего дерева с финальным деревом прошлого run недостаточно:
review мог судить более раннюю ревизию внутри того run.

### Требуемое исправление A

- Сделать принадлежность verdict кандидату устойчивым свойством самой записи
  evidence, доступной reuse, а не только итогового отображения coverage.
- При переносе сохранять исходный fingerprint; не заменять его текущим.
- Проверять актуальность непосредственно перед потреблением verdict. Любая новая
  запись, включая обычный implement dispatch при resume, способна его инвалидировать.
- Учитывать invalidated/stale status предыдущего run. Отсутствие достаточного
  доказательства соответствия кандидату означает отказ от reuse этой проверки.
- Не выбрасывать корректный reuse в неизменившемся контрольном случае. Отдельно
  определить возможность сохранить verdict после dispatch, который не изменил дерево.

## P1-B. RoleContract сравнивает старую роль со старой ролью

Воспроизведение: первый run использует `stage: review, role: reviewer`, затем
останавливается на браузере. В текущем валидном workflow та же стадия назначена
`role: architect`. Обе роли остаются настроены; параметры маршрутизации совпадают.

**Факт:** `role_runs=0`, architect не вызывается. Coverage содержит
`role=architect`, но `profile=loop-review`: прежний reviewer представлен как
выполненная работа другой роли. Итог — `ready_for_human`.

Точки: `TaskLoop.reusableJudgements`, строки 1766–1769;
`routingNow`, строки 1799–1804; `RoleContract.differenceFrom`, строки 107–121.
Аргумент `role` берётся из старой строки шага, текущая стадия предоставляет
только routing. В результате сравниваемый ключ `role` не отражает её новую роль.

Нужно передавать текущую `Workflow.Stage` целиком и сравнивать её роль, вид стадии
и применимые зависимости evidence с записанным контрактом. Проверять, что старый
профиль действительно может удовлетворить текущей роли. Совпадение stage ID не
заменяет эту проверку.

## Воспроизведения и следующее задание

Локальные исходники:

- `out/review-opus-verification/ResumeProbe.java` — A1 и B.
- `out/review-opus-verification/StaleProbe.java` — A2.
- `out/review-opus-verification/RepairingVendor.java` — stub, меняющий исходники
  при repair. Вызывает штатный `StubVendor`, затем добавляет проверяемую дельту.

Summary сохранены рядом: `writer-changed.json`, `role-changed.json`,
`stale-prior.json`, `stale-resumed.json`. Пробы печатают факты, но не являются
добавленными в suite assertion-тестами. Конфигурация перед resume валидируется,
а retry разрешается через `ApprovalStore`.

Opus: сначала перенести эти три сценария в `TaskLoopTest` с assertions, показывающими
нынешние дефекты; затем исправить общую проверку применимости verdict и повторить
тесты. Контрольные случаи budget-only resume и полностью неизменившийся кандидат
должны сохранить экономию вызовов. Проверить также, что JSON, report text и human
gate одинаково описывают реальную проверку кандидата.

До принятия этого исправления не переходить к planner или смене implementer/reviewer:
смена ролей будет непосредственно попадать в дефект B. После закрытия P0 следующий
этап прежний — устойчивые ID findings и история прогресса, затем planner и эскалация
с writer provenance. Перед следующим live восстановить отдельную конфигурацию
прогона из проверенных источников, не принимать удалённый `out` за сохранённую настройку.
